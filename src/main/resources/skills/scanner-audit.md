# Scanner and audits

1. Confirm scope (`scope(action=check)`). `scanner(action=start_crawl)`'s `in_scope_only` is enforced by filtering seeds before crawling; its `max_depth` is NOT — Burp's Montoya API has no depth control, so it's always ignored (check the response's `ignored` field).
2. `scanner(action=start_crawl)` and/or `scanner(action=start_audit)`; each returns a task. `start_audit`'s `urls` are added directly; `audit_mode=thorough` currently runs identically to `normal` (Montoya has only two built-in audit configurations); `insertion_point_types` is accepted but not enforced; `crawl_first` starts a real, separate crawl when `urls` is given, but its discoveries are NOT auto-added to this audit (poll the site map after and start a fresh audit with what you find) — read each response's `applied`/`ignored`/`crawl_note` fields rather than assuming every parameter took effect. `auth_header_name` + `auth_header_value` set one header (replacing the request's own value) on Scanner traffic to the audited hosts only, until the audit ends or is deleted; a `Cookie` value sets only the cookies it names and keeps the request's other cookies (the Scanner's cookie payloads, CSRF and load balancer cookies). An audit with an auth header and no resolvable host is refused.
3. Track with `scanner_task(action=list)`, `scanner_task(action=status)`, `scanner_task(action=issues)`; add requests with `scanner_task(action=add_request)`; stop with `scanner_task(action=delete)`. Burp's own `request_count`/status for a crawl can be unreliable (stuck at 0 on some Burp versions) — `scanner_task(action=status)` also reports `sitemap_new_entries`, a heuristic based on `sitemap(action=query)` counts; prefer it for judging whether a crawl is still finding new pages. When Burp cannot list a task's issues, `scanner_task(action=issues)` falls back to the site map's issues under the task's targets, marked `"source": "site_map"`.
4. Read results: `scanner(action=get_all_issues)`, `sitemap(action=get_issues)` (severity filter includes `FALSE_POSITIVE`); export with `scanner(action=generate_report)`. To see what a crawl actually found, `sitemap(action=query, only_with_response=true)` — it excludes noise (`/cdn-cgi/`, favicon, etc.) by default and reports `with_response`/`without_response` counts and status/MIME histograms, unlike a raw site map dump.
5. Create issues yourself: `scanner(action=create_issue)`, `sitemap(action=add_issue)`. Mark entries worth returning to with `sitemap(action=annotate)`.

## Custom checks
- BChecks: `custom_check(action=bcheck_templates)` first, then `custom_check(action=bcheck_create)` (types `passive_response`, `passive_request`, `insertion_point`, `host_level` with its own `path`, `path_level`, `collaborator`; any text is written into the script as a string, never as DSL; an empty pattern is rejected), `custom_check(action=bcheck_import)` for a hand-written script, `custom_check(action=bcheck_list)`, `custom_check(action=bcheck_remove)`.
- Script-mode scan checks: `custom_check(action=scancheck_templates)`, `custom_check(action=scancheck_create_passive)` (conditions joined by `match_mode=all|any`), `custom_check(action=scancheck_create_active)` (payload steps, each with its own `match_mode`; `stop_if_no_match=false` makes a step optional; a step without response conditions only primes the target, so it counts once answered but is never evidence). An active check reports only when a step matches and the unmodified request would not have matched the same conditions; that unmodified request is sent before the first payload, so a payload the application stores cannot hide its own match. `custom_check(action=scancheck_list)`, `custom_check(action=scancheck_remove)` (id or name).
- Dry runs before deploying: `custom_check(action=bcheck_dry_run)` and `custom_check(action=scancheck_dry_run)` take the same definition and evaluate it against the proxy history already recorded (`url_pattern`, `in_scope_only`, `max_items`, `max_matches`). Nothing is imported or sent: a passive check lists what it would report; an active one shows how many recorded responses already satisfy its conditions without a payload (a high count means the conditions are too broad).
- `scanner(action=register_check)`, `scanner(action=unregister_check)` (id or name) and `scanner(action=import_bcheck)` are the lower-level routes. Creating a check under an existing name replaces it.
- Bambdas: `bambda_templates` (envelope format, known functions and locations, starting templates), then `bambda_import` (an envelope or a bare lambda body; the result carries its `id`, and importing that id again replaces it).

Pause or resume Burp's task engine with `burp(action=task_engine_set)` / `burp(action=task_engine_state)`.
